# yt-dlp 導入と更新 要件定義書

## 1. 目的

yt-dlp を GitHub のリリースから導入し、プロセスの再起動なしに新版へ切り替える。API とワーカーが同じ導入済みの版を使い、更新は1か所が担う。glibc と musl のどちらの Linux でも、その環境で動く公式バイナリを選べる。

## 2. スコープ

### 2.1 対象

- 新版の確認、取得、検証、切り替え、古い版の削除。
- libc とアーキテクチャに応じた取得物の選択。
- 初回の導入と、同梱の版へのフォールバック。
- 確認の時刻、導入中の版、直近の失敗の記録。

### 2.2 対象外

- yt-dlp のリリース署名の検証。
- yt-dlp のプラグインの更新。
- 更新の契機を発行する側の動作。

## 3. 前提

- なし

## 4. 機能要件

- FR-1: 新版の確認は、起動時と一定間隔ごとに、GitHub の最新リリースの転送先から版を得て行い、新版のときだけ取得する。
- FR-2: 取得物は、同じ版のチェックサム一覧と一致し、実行して期待する版を返すときだけ適用する。
- FR-3: 適用は、現在の版を指すリンクの原子的な切り替えで行い、実行中のプロセスは旧版で完走する。
- FR-4: 確認、取得、検証のいずれかが失敗しても、導入済みの版を使い続け、失敗を記録して短い間隔で再確認する。
- FR-5: 新版確認の依頼は、前回の確認から最短間隔が経過しているときだけ受け付ける。
- FR-6: 確認の時刻、導入中の版、更新の時刻、直近の失敗を Redis に記録する。
- FR-7: 導入先は版ごとのディレクトリと現在の版へのリンクからなり、直近の指定数の版を残して古い版を削除する。
- FR-8: 取得するバイナリは、glibc か musl か、x86_64 か aarch64 かで決め、未対応のアーキテクチャは実行時エラーにする。
- FR-9: 導入先が空か壊れているときは、イメージまたはインストール時に同梱した版で動く。
- FR-10: 導入先が空のときだけ初回の版を取得し、失敗したらビルドまたはインストールを失敗させる。
- FR-11: 取得元、確認間隔、再確認間隔、最短間隔、保持数を環境変数で変更できる。

## 5. 非機能要件

- NFR-1: 待機中の新版確認は、確認1回につき HEAD 要求1回とし、API の利用と pypi.org への接続は 0 回とする。
- NFR-2: 新版の確認の既定間隔は 21600 秒、失敗後の再確認の既定間隔は 1800 秒とする。

## 6. 受け入れ条件

- AC-1 (FR-1): 前回の確認から間隔が経過していないと確認せず、経過していると確認して新版を取得する。
- AC-2 (FR-1): 最新の版が導入中の版と同じなら、取得しない。
- AC-3 (FR-2): チェックサムが一致しない取得物、または報告する版が異なる取得物は適用されない。
- AC-4 (FR-3): 適用後は現在の版へのリンクが新しい版を指し、切り替えの途中の状態が観測されない。
- AC-5 (FR-4): 確認が失敗しても導入済みの版のリンクは変わらず、失敗が記録される。
- AC-6 (FR-4): 失敗の後は、通常の間隔ではなく短い再確認の間隔で再確認される。
- AC-7 (FR-5): 前回の確認から最短間隔が経過していない依頼では、確認が行われない。
- AC-8 (FR-6): 確認後に、確認の時刻と導入中の版が Redis に記録される。
- AC-9 (FR-7): 指定数を超える古い版が削除され、現在の版は残る。
- AC-10 (FR-8): glibc と musl の x86_64 と aarch64 で、それぞれ対応するバイナリ名が選ばれる。
- AC-11 (FR-8): 未対応のアーキテクチャでは実行時エラーになる。
- AC-12 (FR-9): 実行環境の検索パスは、導入先の現在の版を先に、同梱の版を後に並べる。
- AC-13 (FR-10): 現在の版のリンクがあれば取得せず、取得が失敗すると例外が呼び出し元へ伝わる。
- AC-14 (FR-11): 環境変数の指定が設定に反映され、未指定のときは既定値になる。
- AC-15 (NFR-1): 新版の確認は github.com への HEAD 要求だけを行い、pypi.org を参照しない。
- AC-16 (NFR-2): 設定の既定値が 21600 秒と 1800 秒である。
