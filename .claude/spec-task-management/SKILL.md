# 仕様駆動タスク管理（機能単位）

`requirements.md`（要件）・`design.md`（設計）・`tasks.md`（タスク）の3点セットを使い、タスク管理を機能実装の単位で行うための作業方式。新機能に着手してからcommitするまでの通常運用と、既存プロジェクトのWBS/フェーズ計画をこの方式へ統合・移行する作業の両方をカバーする。WBSのような「実施順・フェーズ」を管理する横断的な別ディレクトリは新設しない。

## 基本方針

1. **タスクは「機能実装の単位」で管理する。** WBSのような横断的な番号体系・別ディレクトリを新設しない。`tasks.md`の見出し（`## <機能名>`）が管理の単位になる。
2. **1機能が複数の区切りに分かれる場合は、その機能の見出しの中でフェーズ・ステップを分ける。** 例: 見出しに`（Phase N）`と付記する、または`### Step 1: ...`のような内部小見出しを切る。**機能をまたぐ独立の番号体系（全機能通し番号のPhase一覧）は作らない。** Phase/Step番号は「その機能が何度目の改訂か」を示す内部ラベルとしてのみ使い、design.mdの該当節と対応させる索引に使う（`design.md`側にも同じ`Phase N`表記があると、両者の対応が取りやすい）。
3. **確定した仕様と、作業の記録を明確に分ける。**
   - `design.md` / `requirements.md`: 実施済みの機能について、確定した仕様（アーキテクチャ、インターフェース、データ構造、既知の制約、決定の理由）を「事実」として記載する。検討過程や発見した不具合の顛末そのもの（narrative）は残さない。ただし、決定の理由が今も判断根拠として有効なら、1〜2文に圧縮して残してよい。
   - `tasks.md`: 「何を実施し、どう検証したか」の記録に留める。チェックリスト（`- [x]`/`- [ ]`）と簡潔な検証結果（環境・方法・件数・既知の未検証事項）程度に圧縮する。確定仕様の一次情報は常に`design.md`側に置き、`tasks.md`に同じ内容を書き写さない。
4. **複数アプリケーション（サービス）構成の場合、全体用とアプリ個別用を書き分ける。** ルートの`tasks.md`は横断的なタスク・将来課題・実装状況の索引に留め、各アプリ固有の詳細はそのアプリの`tasks.md`を一次情報とする。1機能が複数アプリにまたがる場合は、各アプリの`tasks.md`へ分割して書く。
5. **commitは機能単位で作成する。** 1機能=1commit、実機検証まで完了してからcommitする、複数機能の変更を1commitに混在させない、といった規則をプロジェクトの運用規則文書（AGENTS.md相当）に明記する。
6. **可読性のため、設計書には表・mermaid図を積極的に使う。** 人間もレビューする前提のドキュメントなので、箇条書きの羅列より、状態遷移・コンポーネント関係は図（mermaid）、対応表・比較は表にまとめる。冗長な説明文を削り、要点を残す。

7. **作業中に見つけた、現在の作業スコープに関係のない不具合・課題は、その場で直さず`tasks.md`へ積み残しとして記録する。** 直すと機能単位のcommitに無関係な変更が混ざり、検証範囲も曖昧になるため。記録先は、影響するアプリケーションの`tasks.md`（複数にまたがる・アプリを特定できないものはルートの`tasks.md`）の「積み残し」節とし、次の内容を書く: 現象（どこで何が起きるか）、原因が分かっていればその箇所（ファイル・行・変数名）、修正案、再現条件・発見した状況（日付・環境）。別のセッションがその記録だけで着手できる粒度にする。記録は、その時点の機能単位のcommitとは別に（設計書のみの修正と同じ扱いで）単独でcommitしてよい。現在のスコープを妨げる不具合（直さないと検証が完了しないもの）は積み残しにせず、その機能単位の中で直す。

## 新機能に着手する時の標準フロー

実装に着手する前に、次の順で`specs/`（複数アプリ構成なら該当する`specs/<アプリケーション名>/`）を更新する。

1. **要求を`requirements.md`に記載する。** 何を実現するか（目的・要求・制約・非機能要件）を先に固める。実装手段（技術選定・データ構造・API仕様）には踏み込まない。
2. **設計を`design.md`に記載する。** どう実現するか（アーキテクチャ、コンポーネント間の責務分担、インターフェース、データ構造、技術選定とその理由）を、実装前に決定事項として書く。複数アプリにまたがる機能の場合、全体用`design.md`には役割分担の要約と各アプリの`design.md`への参照だけを書き、実装詳細（エンドポイント一覧・リクエスト/レスポンス形状等）はそれを実装するアプリの`design.md`を一次情報とする。同じ詳細を全体用・個別用の両方に書き写さない。
3. **`tasks.md`に機能見出しを起票する。** `## <機能名>`の見出しを追加し、実施予定のタスクを`- [ ]`のチェックリストで書き出す。この段階では`design.md`該当節への参照で足り、確定仕様の詳細を書き写さない。1機能が複数の区切り（設計→実装→検証、複数ステップ）に分かれる場合は、その見出しの中で`### Step 1: ...`や`（Phase N）`のような内部区切りを使う。機能をまたぐ独立の番号体系（全機能通しのPhase一覧）は作らない。
4. **実装する。** 実装中に`design.md`の決定と食い違いが生じたら、その場で`design.md`を更新する。実装が終わってからまとめて直そうとすると、乖離が次の棚卸しまで気づかれずに残る。
5. **その機能の主要タスクの実装がすべて終わった最後に、まとめて実機検証する。** 個々のタスクごとに都度検証しない（手戻りが分かった時点でまとめて直せるようにするため）。ここでの「実機」は開発者が用意する検証用環境を指し、実運用相当ハードウェアでの検証は別途明記された場合のみ行う。
6. **`tasks.md`のチェックボックスを実施済みへ更新し、検証結果を書く。** フォーマットは後述。検討過程・発見した不具合の経緯そのもの（narrative）は残さず、決定理由が判断根拠として今も有効なものだけを1〜2文に圧縮して`design.md`側に残す。
7. **実機検証まで完了してから、その機能単位で1つのcommitを作る。** 実装commitと検証commitに分割しない。複数機能単位の変更を1commitに混在させない。前の機能単位が未コミットのまま次の機能単位の作業に入らない。commitメッセージの1行目は`<機能名>の<状態>（<内容>）`形式（例: `接続先選択UIの刷新の実装完了・検証完了（ping順リスト・お気に入り対応）`）。

設計書のみの修正（実装を伴わない要件追加・設計の見直し）は、実装の着手を待たず、その修正の区切りごとに単独でcommitする。設計検討だけで終わるセッションでも、内容を未コミットのまま次のセッションへ持ち越さない。

## `tasks.md`の記載フォーマット例

```markdown
## <機能名>（Phase N、検証完了）

- [x] <実施したタスク>（要点。ファイル名・関数名等の目印を添える）
- [x] <実施したタスク>
- [ ] <未実施のタスク>（未実施の理由・条件を一言添える）

検証: <検証環境>で<検証方法>を実施し<結果概要・件数>を確認。既知の未検証事項: <あれば>。
```

複数アプリ構成のルート`tasks.md`には、索引として次のような状態一覧表を置くと、人間・Claude双方が全体の実装状況を素早く把握できる（wbs的な「実施順」は持たず、状態と参照先だけを示す）。

```markdown
| 機能 | 対応アプリ | 備考 |
|---|---|---|
| <機能名> | api, web | <未検証事項があれば> |
```

## アンチパターン

- 作業中に見つけたスコープ外の不具合を、その機能単位のcommitへ混ぜて直す。または、見つけたのに記録せず次のセッションへ伝わらないまま放置する（基本方針7）。
- 実装に着手する前に`requirements.md`/`design.md`を確定させず、コードを書きながら仕様を事後的に書き足す。仕様書がcommit後の実装を後追いする記録になり、確定仕様の一次情報として機能しなくなる。
- 機能単位の途中でcommitを分割し、実装commitと検証commitに分かれてしまう。あるいは検証未了のまま「実装完了・検証待ち」の状態でcommitしてしまう。
- 複数アプリにまたがる機能で、全体用`design.md`と個別アプリ用`design.md`に同じ実装詳細を二重に書く。
- WBSを廃止したのに、別の横断的な番号体系（全機能を貫くPhase通し番号の一覧）を新設してしまう。Phase/Step番号は個々の機能の中の内部区切り・design.mdとの対応キーとしてのみ使い、プロジェクト全体を貫く時系列インデックスとしては使わない（一覧性が必要なら「状態一覧の表」で足りる。番号に依存させない）。
- `tasks.md`に確定仕様の詳細（エンドポイント一覧やアーキテクチャ判断そのもの）を書き、`design.md`と二重管理になる。
- 大量の細かい参照修正をエディタで1件ずつ処理し、往復コストで作業が長引く（移行作業時）。
- 移行を「コピー」で済ませ、既に陳腐化した記述（未検証のまま・推測のまま）をそのまま転記してしまう（移行作業時）。
- 旧ディレクトリを消す前にリポジトリ全体を検索せず、コードコメントやテストスクリプトにリンク切れの参照を残してしまう（移行作業時）。

## 既存のWBS/フェーズ計画を統合する場合（移行作業）

新規プロジェクトでこの方式を最初から採用する場合は前段の標準フローだけで足りる。既存プロジェクトにWBS・ロードマップ・phaseN.md群のような横断的な別ディレクトリが残っている場合のみ、以下の移行手順を使う。

1. **全体像の把握を1回で済ませる。** 既存のWBS/フェーズファイルと現行のspecsを、それぞれ`cat file1 file2 ... > scratch.txt`のように一括結合してからまとめて読む。1ファイルずつ読みに行く往復を避ける。大規模プロジェクトほど、この往復コストが作業時間の大半を占める。
2. **先に現行specsの充実度を確認する。** 移行先（design.md/requirements.md）が既にどこまで確定事実を書けているかを、着手前に確認する。仕様駆動開発を既に運用しているプロジェクトでは、design.mdは既にほぼ最終形を記述済みで、実際に手を入れるべきはtasks.md側（チェックリストの網羅性・旧ディレクトリへの参照除去）だけ、ということが多い。「全部書き直す」前提で臨むと過剰な作業になるので、まず差分を見極める。
3. **フェーズ→機能→所属アプリのマッピングを先に決める。** 複数アプリ構成なら、各フェーズ・機能がどのアプリに属するかを一覧化してから着手する（頭の中で構わないが、フェーズ数が多い場合は簡単な対応表を作った方が手戻りが少ない）。
4. **転記する前に情報を3種に仕分ける。**
   - 確定仕様（アーキテクチャ、インターフェース、既知の制約、今も有効な決定理由） → `design.md` / `requirements.md`
   - 実施記録（チェックリスト、検証環境・方法・件数） → `tasks.md`
   - 使い捨てのnarrative（不具合発見の経緯、検討して不採用にした案、セッション再開時の申し送りメモ、番号体系の変遷の言い訳） → 基本的に破棄する。決定自体が今も有効ならdesign.mdへ一言で圧縮し、経緯そのものは残さない。
5. **旧ディレクトリへの参照をリポジトリ全体から洗い出す。** `grep -rl` を、specs配下だけでなく、コードコメント・E2E/テストスクリプト・CI設定・README等リポジトリ全体に対してかける。ディレクトリを消した後にリンク切れの参照が残るのを防ぐ。
6. **既存タスク一覧の「書かれたまま古くなった記述」を積極的に直す。** 移行はコピー作業ではなく監査の好機である。「未検証」「不明」「推測」「未実施」と書かれたまま長期間放置されている項目は、後続の機能で実際に検証・確認済みになっていることが多い。該当箇所を洗い出し、実際に確認できた事実へ更新する（例: 実機検証が完了しているのに「未検証」のままだった記述、CI実行前提のまま「未実行」と書かれていたが実際は成功していた記述、挙動が「推測」のままだったが後続の調査で確定していたもの）。こうした食い違いは、design.mdとtasks.mdの見出し・状態を突き合わせるだけで見つかることが多い。
7. **移行漏れを検出する。** design.mdには存在するのに、対応する機能単位がtasks.mdに存在しない（＝実装はされたがタスクとして記録されなかった）ケースを探す。design.mdの見出し一覧とtasks.mdの見出し一覧を突き合わせると見つけやすい。
8. **機械的な参照除去は一括処理する。** 「あるディレクトリ・ファイルへの参照を全部消す」ような単純作業は、ファイルごとにエディタで潰すより、対象行を確認した上でスクリプト（Python/sedの文字列置換）で一括適用する方が速く安全。適用後、構文チェック（`bash -n`等）とテストスイート・lintを流し、コメント以外を壊していないか確認する。
9. **運用ルール文書（AGENTS.md相当）を最初に書き換える。** 個々のtasks.mdを直す前に、プロジェクトの運用規則（コミット規則・仕様駆動開発の節）を新しい語彙（「フェーズごと」→「機能単位ごと」等）に揃えておく。後から各ファイルを直す際に表記のブレが出ない。
10. **最後に旧ディレクトリを削除し、テスト・lint・（あれば）中立性検査等を実行してから1つのcommitにまとめる。** ドキュメントのみの変更でも、コード内コメントに手を入れた場合は必ずテストスイートを流して確認する。
